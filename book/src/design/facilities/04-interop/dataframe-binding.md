# How std.dataframe wraps its engine

[`std.dataframe`](../../stdlib/dataframe.md) calls a Rust engine built on
Polars through a C ABI, and its values may be moved to, shared by and dropped
on worker threads. This page shows how the binding meets the
[opaque thread contracts](trusted-declarations.md#opaque-types-on-worker-threads)
and how to audit it. Use the same steps for any Rust or C library.

The binding has three layers:

| Layer | File | Role |
|---|---|---|
| Engine | `plenty-dataframe/src/*.rs` | `pldf_v1_*` C exports over Polars types, one Box per handle |
| Declarations | `stdlib/std/dataframe.plentyi` | `opaque` types and `extern def` calls, all private |
| Facade | the same file | owner classes and the public API |

## Classify every engine type

Start from what each call does to the pointee:

- A type that no call writes through after construction is
  `@thread_shareable`. `DataFrame`, `Column`, `Expr`, `Query`, `Exprs`,
  `SortKeys`, `CsvSchema`, `Error` and the result buffers are all of this kind.
- A type built up in steps gets a separate `@thread_movable` builder. A
  frame gains columns one at a time, an expression list or sort key list
  gains entries, and a CSV schema gains overrides.

| Builder (`@thread_movable`) | Calls | Finished type (`@thread_shareable`) |
|---|---|---|
| `RawFrameBuilder` | `frame_builder_new`, `frame_builder_add` | `RawFrame` |
| `RawExprsBuilder` | `exprs_builder_new`, `exprs_builder_add` | `RawExprs` |
| `RawSortKeysBuilder` | `sort_keys_builder_new`, `sort_keys_builder_add` | `RawSortKeys` |
| `RawCsvSchemaBuilder` | `csv_schema_builder_new`, `csv_schema_builder_add` | `RawCsvSchema` |

Every builder also has `_finish` and `_drop` calls. Splitting the types keeps
the [mutation rule](trusted-declarations.md#when-a-binding-may-mark-a-type)
exception-free: no call writes through a shareable pointer, so concurrent
calls on a shared frame cannot race.

## Assert the promises in the engine

The engine states each promise as a Rust bound, so a change that adds a
non-thread-safe field fails to compile. Each read-only type has exactly one
release function, generated by `destroy!`, which asserts `Send + Sync`:

```rust
macro_rules! destroy {
    ($name:ident, $ty:ty) => {
        const _: () = {
            const fn send_and_sync<T: Send + Sync>() {}
            send_and_sync::<$ty>();
        };
        release!($name, $ty);
    };
}
```

`builder!` declares a builder as a `repr(transparent)` wrapper around its
finished type, asserts only `Send`, and generates `_new`, `_finish` and
`_drop`. Because the two types share a layout, `_finish` returns the same
pointer with its new type. It moves the Box without copying or allocating, so
it cannot fail:

```rust
#[repr(transparent)]
pub struct FrameBuilder(DataFrame);

pub unsafe extern "C" fn pldf_v1_frame_builder_finish(raw: *mut FrameBuilder) -> *mut DataFrame {
    raw.cast()
}
```

Only the `_add` calls take a `*mut` handle, and each takes a builder. Every
other call takes `*const` handles and writes only to output slots it creates.

## Declare the contracts

The declarations mirror the engine: one annotation per `opaque`, and
`@thread_safe` on every call that takes or returns one. The compiler rejects a
missing `@thread_safe` on such a call.

```plenty fragment
@thread_shareable
opaque RawFrame
@thread_movable
opaque RawFrameBuilder

@thread_safe
extern def frame_builder_new(out: &mut RawFrameBuilder) -> RawError = "pldf_v1_frame_builder_new"
@thread_safe
extern def frame_builder_add(builder: RawFrameBuilder, column: RawColumn) -> RawError = "pldf_v1_frame_builder_add"
@thread_safe
extern def frame_builder_finish(builder: RawFrameBuilder) -> RawFrame = "pldf_v1_frame_builder_finish"
@thread_safe
extern def frame_builder_drop(builder: RawFrameBuilder) -> () = "pldf_v1_frame_builder_drop"
@thread_safe
extern def frame_drop(raw: RawFrame) -> () = "pldf_v1_frame_drop"
```

`&mut RawFrameBuilder` is an output slot: the call stores a new pointer there.
The declaration cannot say whether a call writes through an existing pointee,
which is why the engine-side bounds and the audit below matter.

## Own every pointer in one class

Each raw type has one owner class whose private field holds the only copy of
the pointer, and `__del__` releases it. Release functions accept null, so an
owner whose construction failed releases nothing. The destructor also makes
`copy(x)` reject the owner, which is the form the compiler accepts for a
`@thread_movable` field crossing threads.

Keep the `opaque` declarations private, as `std.dataframe` does, and the
pointers behind private owner fields. The compiler checks the type a pointer
crosses in, not how many owners hold it; privacy is what confines the code
that could copy a pointer into a second owner to the binding module, where
the audit below covers it.

```plenty fragment
pub class DataFrame:
    raw: RawFrame
    def __init__(self) -> ():
        self.raw = RawFrame.null()
    def __del__(self) -> ():
        frame_drop(self.raw)

class FrameBuilder:
    raw: RawFrameBuilder
    def __init__(self) -> ():
        self.raw = RawFrameBuilder.null()
    def __del__(self) -> ():
        frame_builder_drop(self.raw)
    def finish(self: &mut FrameBuilder) -> DataFrame:
        mut out = DataFrame()
        out.raw = frame_builder_finish(self.raw)
        self.raw = RawFrameBuilder.null()
        out
```

`finish` moves the pointee to the new owner and clears the builder, so
exactly one owner releases it. The public constructor uses the builder only
locally:

```plenty fragment
pub def frame(columns: &list[Column]) -> Result[DataFrame, DataFrameError]:
    mut builder = FrameBuilder()
    checked(frame_builder_new(&mut builder.raw))?
    for column in columns:
        checked(frame_builder_add(builder.raw, column.raw))?
    Ok(builder.finish())
```

On every error path the builder has not been finished, and its `__del__` frees
it. After `finish` nothing can fail, so no path leaks or double-frees.

A `@thread_movable` builder may only cross threads as a field of a moved
owner that `copy(x)` rejects. The facade never lets one escape, but the contract keeps a future
change honest: sharing a builder is a compile error.

## Audit each call

The annotations promise behavior that the compiler cannot see. Audit every
`pldf_v1_*` export, and repeat the audit when it changes:

1. **Handle arguments.** A shareable handle must be `*const` and read only.
   `*mut` appears only on builder handles and output slots. Search the
   exports for `*mut` parameters that are not `*mut *mut` output slots.
2. **Shared state.** The engine keeps no `static mut`, thread-local or global
   cache, and its own types add no interior mutability (`Cell`, `RefCell`,
   `Mutex`, atomics). The `Sync` bound guarantees that any cache inside a
   Polars type is synchronized and invisible to callers.
3. **Thread affinity.** No handle is tied to its creating thread. Polars runs
   work on its global pool, which accepts jobs from any thread.
4. **Panics and errors.** Every call that returns an error runs inside
   `boundary`, which catches panics and returns an owned error, so no
   unwinding crosses Plenty frames. `_finish` is a pointer cast and release
   functions only drop a Box.
5. **Ownership.** Each `_new` or constructor writes one new Box to a null
   output slot; each release function frees it once; `_finish` transfers it.
   No call retains an argument pointer after returning.

The `Send` and `Sync` bounds check the field types behind items 2 and 3.
Items 1, 4 and 5 rest on review and on the engine's own tests.

## Test on workers

`tests/fixtures/dataframe_workers.plenty` moves frames to workers, shares one
through `Shared`, builds a query on one thread and collects it on another, and
drops values on workers. The normal suite type-checks it without the engine;
the dataframe engine job runs it, as described in
[Install the dataframe engine](../../stdlib/dataframe-engine.md#development-checks).
The engine crate's own tests cover finishing, releasing an unfinished builder
and finishing null.
