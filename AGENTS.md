# Local worktrees, issue claims, and pull requests

- Issues and PRs are entirely local records in the shared `issues.db`. Do not create GitHub PRs/issues, add GitHub URLs, or fetch/push as part of this workflow.
- Before starting an issue, read its comments and linked PRs, then **claim it through an issue comment** using `scripts/issue_claim.py` as documented in `CLAUDE.md`. The helper checks and inserts under one SQLite write transaction. If another agent has an active claim, do not start work on that issue; choose another unclaimed issue or report the blocker. Checking first and posting an ordinary comment separately is not an atomic claim.
- Use a unique author label per agent/task. Continue an existing claim only when it belongs to your assigned task; do not impersonate its owner. Claims remain active during implementation, review, and revisions. Never assume a claim has expired. Only its owner releases it, or the user explicitly authorizes a handoff; record releases as comments, preserving history.
- Use a dedicated local branch and worktree for each independent task/worker, based on the local target branch (normally `main`). Reuse the assigned worktree, claim, and PR when continuing a task. Do not implement changes in the main worktree or on the target branch.
- Inspect local changes and existing worktrees before starting. Preserve other workers' and the user's changes; never reset, stash, or commit them as part of your task.
- Agree on responsibility for files/components before concurrent work. Keep independent tasks in separate PRs; identify dependencies between PRs instead of silently copying unmerged work. Worktree isolation does not prevent conflicting designs or overlapping edits.
- A request to make repository changes includes committing only the task's changes locally and creating/updating a `pull_requests` record via `../issues-browser/cli.js`. See `CLAUDE.md` for exact commands, including target branch, worktree, and description. No remote publication is involved.
- Link each relevant issue using a PR title such as `Fixes #15: ...`, or an issue comment with its `pull_request_number` foreign key (CLI `comment --issue 15 --pr N`). All these numbers refer to the local database. Plain prose mentioning a PR number alone does not create a structured link.
- The user reviews and merges local PRs. Do not merge or rewrite a branch under review unless explicitly instructed. Leave the branch and worktree available for review and follow-up. PR status changes are metadata only; setting `merged` does not merge Git branches or close issues.
- Include relevant implementation, tests, reference/tutorial changes, and minimal backlog edits in the same PR. State the problem, resulting behavior, validation actually performed, and remaining limitations. Hand off the local PR number, branch, target, and worktree path.
- **Shared issues register exception:** every worktree must read and update `issues.db` in the main (primary) worktree, using its absolute path. Never use a task worktree's tracked copy or replace it with a symlink. Use SQLite transactions and a busy timeout; see `CLAUDE.md` for path discovery and commands. Shared issue metadata is updated directly, but an issue fixed by a PR stays open until that PR is merged. Do not stage stale worktree copies of `issues.db` in feature PRs.

# Project conventions

- Docs are an mdBook in `book/src/`. `SUMMARY.md` lists every page in reading order.
- Track future work and priorities only in `book/src/backlog.md`. Root `BACKLOG.md` is a link to that page. Issue ownership, comments, and PR review status belong in the shared `issues.db`. Reference pages describe implemented behavior and limits; proposals record rationale and alternatives, not competing work queues.
- Always aim to keep the reference (`book/src/design/`) up to date with the latest design decisions and architectural changes.
- ...and likewise, always aim to keep the implementation up to date with the latest design decisions in the reference.
- Keep the tutorial (`book/src/tutorial/`) up to date with learner-visible language changes. Teach implemented behavior with runnable examples; `tests/test_tutorial.rs` checks the guide's examples and expected diagnostics directly.
- Keep pages small. Add a new page to `SUMMARY.md`; `tests/test_tutorial.rs` fails if a page is missing from it.
- A `plenty-file` companion module must be on the same page as the example that uses it.
- Record defects and gaps in implemented behavior (crashes, misleading diagnostics, missing operations, performance concerns) in the SQLite issues register `issues.db`, not in the backlog. Search it (`issues_fts`, FTS5) before adding, and include a reproduction and a suggested fix in the markdown `details`. Set `severity` to `low`, `normal`, or `high`, and work through open issues highest severity first. When an issue is scheduled, cite `issue #N` in the backlog entry; to close one, set `status` to `closed` and fill `resolution` with the fixing commit or the reason it will not be fixed. Never delete issues. See `CLAUDE.md` for schema and commands.
