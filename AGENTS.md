# Local worktrees, issue claims, and pull requests

- Issues and PRs are entirely local records in the shared `issues.db`. Do not create GitHub PRs/issues, add GitHub URLs, or fetch/push as part of this workflow.
- Before starting an issue, read its comments and linked PRs, then **claim it through an issue comment** using `scripts/issue_claim.py` as documented in `CLAUDE.md`. The helper checks and inserts under one SQLite write transaction. If another agent has an active claim, do not start work on that issue; choose another unclaimed issue or report the blocker. Checking first and posting an ordinary comment separately is not an atomic claim.
- Use a unique author label per agent/task. Continue an existing claim only when it belongs to your assigned task; do not impersonate its owner. Claims remain active during implementation, review, and revisions. Never assume a claim has expired. Only its owner releases it, or the user explicitly authorizes a handoff; record releases as comments, preserving history.
- Use a dedicated local branch and worktree for each independent task/worker, based on the local target branch (normally `main`). Reuse the assigned worktree, claim, and PR when continuing a task. Do not implement changes in the main worktree or on the target branch.
- Inspect local changes and existing worktrees before starting. Preserve other workers' and the user's changes; never reset, stash, or commit them as part of your task.
- Agree on responsibility for files/components before concurrent work. Keep independent tasks in separate PRs; identify dependencies between PRs instead of silently copying unmerged work. Worktree isolation does not prevent conflicting designs or overlapping edits.
- A request to make repository changes includes committing only the task's changes locally and creating/updating a `pull_requests` record via `../issues-browser/cli.js`. See `CLAUDE.md` for exact commands, including target branch, worktree, and description. No remote publication is involved.
- Link each relevant issue using a PR title such as `Fixes #15: ...`, or an issue comment with its `pull_request_number` foreign key (CLI `comment --issue 15 --pr N`). All these numbers refer to the local database. Plain prose mentioning a PR number alone does not create a structured link.
- The user reviews local PRs and authorizes merging. Do not merge or rewrite a branch under review unless explicitly instructed. Leave the branch and worktree available for review and follow-up until then. PR status changes are metadata only; setting `merged` does not merge Git branches or close issues.
- After completing work on an issue, an instruction to **"merge the PR"** authorizes the full completion workflow: merge the branch into its local target, mark the local PR as merged, update the linked issue (close it with the actual fixing commit and resolution when resolved), release the task's claim, update the docs and `book/src/backlog.md` if necessary, and remove the task worktree after confirming its changes are preserved. Preserve unrelated changes and other workers' worktrees. No separate cleanup instruction is needed.
- Include relevant implementation, tests, reference/tutorial changes, and minimal backlog edits in the same PR. State the problem, resulting behavior, validation actually performed, and remaining limitations. Hand off the local PR number, branch, target, and worktree path.
- **Shared issues register exception:** every worktree must read and update `issues.db` in the main (primary) worktree, using its absolute path. Never use a task worktree's tracked copy or replace it with a symlink. Use SQLite transactions and a busy timeout; see `CLAUDE.md` for path discovery and commands. Shared issue metadata is updated directly, but an issue fixed by a PR stays open until that PR is merged. Do not stage stale worktree copies of `issues.db` in feature PRs.
- Agent shells run with `pipefail`, and an `rtk` hook rewrites `grep`, `git log`, and `cargo test`. A pipe into `grep -q` or `grep -m1` exits 141, so a wait loop built on it never ends. Use pipe-free conditions such as `git merge-base --is-ancestor BRANCH main`; see "Shell conditions and pipelines" in `CLAUDE.md`.

# Project conventions

- Throughout the docs, never refer to another chapter or section by position (for example, "the next chapter", "the previous section", or "two chapters later"). Use a descriptive name or topic with a direct link instead, so cross-references remain correct when pages are inserted or reordered. Cross-references are encouraged.

- Prefer implementing standard-library functionality directly in Plenty when it is reasonably small and straightforward to express in the language. Wrapping a Rust or C library needs a concrete justification, such as substantial complexity (SQLite or Polars) or security-sensitive details requiring specialist expertise (cryptography and timing-attack resistance). Do not recreate complex storage engines or security primitives merely to avoid a dependency. Explain the reason for a wrapper when choosing one; existing allocation-failure and other API contracts still apply.

- Credit sources on a `std` module's reference page in a final `## Acknowledgements` section: one bullet per wrapped library, ported code or data, published algorithm, or project the API is modelled on, with a link, its role, and its license when its code or data ships. Credit only what the code, module header, issues, PRs, proposals, or commit messages record. Omit the section when there is nothing to credit. Code or data that ships also needs an entry in `scripts/release/third_party_notices.py` (see `book/src/development/releasing.md`) and a credit in the module header.

- Use the [plenty-search skill](.agents/skills/plenty-search/SKILL.md) for related concepts across docs, source documentation and local issue/PR descriptions. It covers freshness checks, synchronization, source verification and missing setup. Use `rg` for exact symbols and implementation code.

- Docs are an mdBook in `book/src/`. `SUMMARY.md` lists every page in reading order.
- Before writing Plenty code, read the executable syntax cheat sheet, `book/src/design/examples/cheatsheet.md`. Keep it current when syntax changes.
- Look up standard library APIs in the generated signature index, `book/src/design/stdlib/signatures.md`. After changing a public `std` declaration or the module table in `book/src/design/stdlib/index.md`, regenerate it with `UPDATE_STDLIB_INDEX=1 cargo test --locked --test integration test_stdlib_index::`.
- Shared development commands and probe guidance are in `CLAUDE.md` and `book/src/development/workflow.md`, for both Codex and Claude. Before handing off a PR that changes book content, navigation, assets, configuration, or docs build/check scripts, run the full docs CI checks: `python3 -B scripts/check_links.py book/src`, `python3 -B -m unittest discover -s scripts -p 'test_*.py'`, and `python3 -B scripts/build_docs_site.py`. Use the pinned mdBook version in `book/releases.json`. A plain `mdbook build` or source-link check does not validate the published site. Report the complete-site result in the PR; if blocked, explicitly identify the missing check and cause instead of calling docs validation complete. Executable example tests are additionally required when applicable.
- Track future work and priorities only in `book/src/backlog.md`. Root `BACKLOG.md` is a link to that page. Issue ownership, comments, and PR review status belong in the shared `issues.db`. Reference pages describe implemented behavior and limits; proposals record rationale and alternatives, not competing work queues.
- Always aim to keep the reference (`book/src/design/`) up to date with the latest design decisions and architectural changes.
- ...and likewise, always aim to keep the implementation up to date with the latest design decisions in the reference.
- Keep the tutorial (`book/src/tutorial/`) up to date with learner-visible language changes. Teach implemented behavior with runnable examples; `tests/test_tutorial.rs` checks the guide's examples and expected diagnostics directly.
- Keep pages small. Add a new page to `SUMMARY.md`; `tests/test_tutorial.rs` fails if a page is missing from it.
- A `plenty-file` companion module must be on the same page as the example that uses it.
- Record defects and gaps in implemented behavior (crashes, misleading diagnostics, missing operations, performance concerns) in the SQLite issues register `issues.db`, not in the backlog. Search it (`issues_fts`, FTS5) before adding, and include a reproduction and a suggested fix in the markdown `details`. Set `severity` to `low`, `normal`, or `high`, and work through open issues highest severity first. When an issue is scheduled, cite `issue #N` in the backlog entry; to close one, set `status` to `closed` and fill `resolution` with the fixing commit or the reason it will not be fixed. Never delete issues. See `CLAUDE.md` for schema and commands.

# Writing and maintaining the tutorial

- Review examples with the question: **Would we recommend writing this code this way today?** Passing compilation and output checks proves correctness, not that an example teaches a good idiom.
- Teach the simplest clear use of implemented Plenty features for the task. Consider error handling, ownership, allocation costs, and standard-library operations. Do not equate fewer lines, newer syntax, or more abstraction with better code.
- Preserve the learning sequence. An explicit loop or match can be the right way to introduce a concept before teaching a convenience. Explain consequential teaching simplifications and current limitations; do not let them look like general recommendations.
- When a feature or library operation lands, revisit existing lessons and application examples it could simplify, not just the page introducing it. Remove obsolete workarounds where appropriate and update related reference links in the same PR.
- Make larger application examples models of recommended practice using concepts already taught. Preserve useful error information, propagate failures unless recovery is intentional, and make error reporting and exit status consistent with the application's outcome.
- Lead with recommended patterns. Keep legacy behavior, alternatives, and exhaustive contracts in clearly identified notes or linked reference pages. Teach proposed features only after they are implemented.
- Keep examples focused and pages small. Explain why a non-obvious choice matters rather than narrating each statement. Validate changed examples and links using the [tutorial maintenance guidance in CLAUDE.md](CLAUDE.md#tutorial-maintenance).
